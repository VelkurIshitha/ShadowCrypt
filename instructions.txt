# 1. PROJECT OVERVIEW

ShadowCrypt is an offline-first Java desktop application that combines hybrid cryptography and image steganography.

Its purpose is to allow users to encrypt text or arbitrary files, conceal the encrypted information inside an ordinary PNG image, and allow the intended recipient to extract and decrypt the information using their private key.

The application combines two techniques:

**Cryptography:** Protects the actual contents of the message or file.

**Steganography:** Attempts to conceal the existence of the encrypted information inside an image.

The application also provides an image-analysis section that compares the original carrier image with the resulting stego image using visual and numerical metrics.

All operations must happen locally. There must be:
- No backend.
- No cloud processing.
- No external API dependencies.
- No online encryption services.
- No network requirement for normal application functionality.

This is a Java desktop project. Reliability, modularity, security, maintainability, and debuggability are more important than unnecessary features.

# 5. CRYPTOGRAPHIC IMPLEMENTATION

This is a security-focused application. Use Java's established cryptographic providers through JCA. Never invent your own encryption algorithm or implement AES/RSA from scratch.

## A. AES-256-GCM

Use AES-256-GCM for encrypting the actual text or file contents.

Requirements:

- Generate a fresh random 256-bit AES key for every encrypted package.
- Generate a fresh random 12-byte nonce.
- Use a 128-bit authentication tag.
- Use `SecureRandom` for cryptographic randomness.
- Never reuse a nonce with the same AES key.
- Use `Cipher` and `GCMParameterSpec`.
- Support authenticated additional data through `Cipher.updateAAD()`.

The GCM tag must be included in the stored ciphertext output.

## B. RSA-OAEP

Use RSA-3072 for key pairs.

Use:
- RSA-OAEP.
- OAEP digest: SHA-256.
- MGF1 digest: SHA-256.

Explicitly configure OAEP using `OAEPParameterSpec` and the appropriate `MGF1ParameterSpec`.

Do not rely on provider defaults.

RSA is only used to wrap the AES session key. Never attempt to encrypt entire files using RSA.

For RSA-3072, the wrapped AES key must be 384 bytes.

## C. Private-key protection

Protect private keys stored on disk using:

- PBKDF2WithHmacSHA256.
- Initial iteration count: 600,000.
- Random salt.
- AES-256-GCM.
- Fresh nonce.

Benchmark PBKDF2 performance on the target system and document the selected iteration count.

Store the KDF parameters, salt, nonce, and encrypted private-key data in a well-defined versioned key-storage format.

Never save the user's passphrase in plaintext.

Never print passwords, AES keys, private-key bytes, or decrypted sensitive data in logs.

## D. SHA-256

Use SHA-256 for:

- Original file hashing.
- Recovered file hashing.
- Public-key fingerprints.

Compare the original and recovered file hashes to verify exact file recovery.

# 6. STEGANOGRAPHY IMPLEMENTATION

Implement only one steganography algorithm in the initial version:

**Least Significant Bit (LSB) substitution.**

Do not implement Adaptive LSB, DCT, or LSB Matching in the initial build.

## Image requirements

- Accept PNG carrier images only.
- Load images using `ImageIO`.
- Normalize every carrier image to a consistent RGB representation.
- Define consistent alpha handling; embed only in RGB channels.
- Preserve the normalized carrier image as the baseline for analysis.
- Save the output as PNG.

## Embedding order

Use the following deterministic traversal:

1. Row-major pixel order.
2. Left to right.
3. Top to bottom.
4. Red channel.
5. Green channel.
6. Blue channel.
7. Most-significant-bit-first within each payload byte.
8. One payload bit per RGB channel LSB.

The extractor must use exactly the same traversal.

Use correct Java bitwise operations and handle signed Java bytes safely.

The LSB implementation must be independent from the cryptographic implementation.

## Capacity calculation

Use:

Capacity in bytes = floor((width × height × 3) / 8)

This is the theoretical capacity before package overhead.

Always calculate the complete encrypted package size before embedding.

Reject the operation if the complete package exceeds the available capacity.

Do not truncate payloads.

# 7. BINARY PACKAGE FORMAT — SHADOWCRYPT V1

Implement the following agreed versioned binary format.

All integer fields must use big-endian byte order.

There are two layers:

1. Readable outer envelope.
2. Encrypted inner payload.

## A. Outer envelope

| Field | Size |
|---|---:|
| Magic number: SHDW | 4 bytes |
| Version | 1 byte |
| Flags | 1 byte |
| Total package length | 4 bytes |
| Wrapped-key length | 2 bytes |
| Nonce length | 1 byte |
| Ciphertext length | 4 bytes |
| Wrapped AES key | 384 bytes |
| GCM nonce | 12 bytes |
| Ciphertext + tag | Variable |

The fixed bootstrap header is 17 bytes.

The RSA-wrapped key is 384 bytes for RSA-3072.

The nonce is 12 bytes.

The GCM ciphertext length includes the 16-byte authentication tag.

## B. Encrypted inner payload

| Field | Size |
|---|---:|
| Inner magic: DATA | 4 bytes |
| Inner version | 1 byte |
| Payload type | 1 byte |
| Filename length | 2 bytes |
| Filename | Variable |
| MIME length | 2 bytes |
| MIME type | Variable |
| Original data length | 8 bytes |
| Original data | Variable |

Payload types:
- `0x01`: Text.
- `0x02`: File.

Filename and MIME metadata must be inside the encrypted inner payload, not exposed in the readable outer envelope.

Use UTF-8 for strings. Length fields must count encoded bytes, not Java characters.

## C. AES-GCM AAD

Use the exact canonical serialized outer header as AAD.

Include:
- Magic number.
- Version.
- Flags.
- Total package length.
- Wrapped-key length.
- Nonce length.
- Ciphertext length.
- Wrapped AES key.
- Nonce.

Do not include ciphertext in AAD. GCM authenticates ciphertext separately.

The sender must construct the complete outer header before GCM encryption. Since the GCM tag is 16 bytes, ciphertext length is known as inner plaintext length + 16.

The receiver must reconstruct the exact same AAD bytes.

## D. Extraction safety

The extractor must:

1. Read only the fixed 17-byte bootstrap header first.
2. Validate magic number and version.
3. Validate all fixed field lengths.
4. Validate total package length against carrier capacity.
5. Validate internal length consistency.
6. Reject negative, impossible, or oversized lengths.
7. Only then allocate bounded buffers and extract the remaining package.

Never trust lengths from an image before validating them.

# 9. IMAGE ANALYSIS IMPLEMENTATION

Implement the following metrics.

## MSE

MSE = (1/N) × sum((original[i] - stego[i])²)

Calculate it using corresponding RGB channel values from the normalized original image and stego image.

## PSNR

PSNR = 10 × log10(MAX² / MSE)

For 8-bit channels, MAX = 255.

If MSE is zero, display PSNR as infinity or an appropriate identical-image result.

## Difference heatmap

Calculate absolute RGB differences between the normalized original and stego image.

Amplify the differences to make small pixel modifications visually observable.

## Other metrics

Calculate:
- Original and stego PNG file sizes.
- Absolute and percentage file-size difference.
- Payload size.
- Complete package size.
- Theoretical capacity.
- Capacity utilization percentage.
- Embedding time.

All results must come from actual operations.
